01 · DEFINITION

Ontology 是什么？

30 秒答案 Ontology 是一份“机器能读懂的领域说明书”。

它明确告诉系统：这个领域里有哪些对象、对象之间有什么关系、哪些规则成立。如果再加入可以执行的业务动作、权限和审计，就成为常说的 Operational Ontology。

1

对象

现实世界中的人、订单、航班、设备，以及它们的类型。

2

关系

乘客预订航班、飞机执行航班、零件安装在飞机上。

3

规则

航班起飞需要可用飞机和合规机组；维护事件会影响飞机状态。

4

动作

提出换机、重新排班、通知乘客；高风险操作需要审批。

它与几个常见概念的区别

概念主要回答什么和 Ontology 的关系
数据库 Schema数据怎样存？规定表和字段；Ontology 更关注这些数据在现实中代表什么。
Knowledge Graph有哪些具体对象和关系？知识图谱是实例数据；Ontology 是这些节点和边应遵守的语义规则。
W3C OWL怎样正式表达 Ontology？OWL 是一种标准化本体语言，不是 Ontology 的唯一实现方式。[2]
Palantir Ontology企业如何围绕对象运行决策？它把数据、逻辑、Actions 和安全整合为 Operational Ontology。
定义来源：Gruber 在知识工程中把 ontology 概括为“对某种概念化的显式说明”。[1] 直白地说，就是把团队脑中的领域共识明确写出来，使人和机器使用同一套名词、关系与规则。
02 · A CONCRETE EXAMPLE

实际怎么用：航空公司处理航班延误

假设用户问：“A102 航班可能延误，会影响谁？应该怎么处理？”没有 Ontology 时，信息分散在航班、机务、机组和旅客系统中；有了 Ontology，系统看到的是同一个业务世界。

原始系统
flight_db：A102, AC=N7
maintenance：N7, issue=M23
crew：C12, duty_left=45
booking：23 名紧张中转旅客

数据彼此分散，字段名也不统一。LLM 即使读到这些记录，也要猜它们如何关联。

→
Ontology 中的业务世界
Flight A102 使用 Aircraft N7
Aircraft N7 存在 MaintenanceIssue M23
Flight A102 分配 Crew C12
Flight A102 连接 23 个 PassengerItinerary

系统可以沿明确关系找出影响范围，并知道可调用哪些规则和 Actions。

系统为什么“知道”去哪里找？

不是 LLM 看到 A102 后自己猜出来，而是事先做好三件事：

1 · 定义关系

先画好“路线图”

规定 Flight 可以通过 usesAircraft 连到 Aircraft，Aircraft 可以连到 MaintenanceIssue。

2 · 连接真实数据

把字段映射成对象

把航班表的 AC=N7 映射为“A102 使用 N7”；文本中提取的 N7 也要链接到同一架飞机。

3 · 沿关系查询

按路线逐步寻找

从 A102 沿 usesAircraft 找到 N7，再查它的型号、维修问题和相关延误事件。

Flight A102 → usesAircraft → Aircraft N7 → hasIssue → M23

要点：只提取出 A102、N7、M23 还不够；还要确认它们是哪个唯一对象，并建立关系。如果没有关系、共同编号或业务规则，Ontology 也不能凭空知道它们相关。

识别对象

把“A102”解析为唯一的 Flight 对象，而不是文本中的普通字符串。

沿关系查影响

从 Flight 找到 Aircraft、Crew、Passengers、Connections 和 MaintenanceIssue。

调用业务逻辑

延误模型计算预计晚点；机组规则检查执勤时限；成本函数比较换机与等待方案。

执行受控动作

Agent 可以自动通知地勤；换机或批量改签则提交 Action，由值班经理审批后写回系统。

Palantir 为什么适合作为例子？

Palantir 官方把 Ontology 描述为连接数据、逻辑、动作和安全的系统，而不是单纯的数据目录。官方架构文档直接使用航空公司与医院场景说明这种方式：航空场景建模 flights、aircraft、crew 和 scheduling optimizers；医院场景建模 patients、nurse schedules、supplies 和 bed capacity。[3]

航空运营

围绕航班、飞机、机组和旅客连接实时状态，支持日常运营和长期计划。

医院调度

连接患者、床位、护士与物资，围绕患者流程做资源决策。

产品落地

Foundry 接入数据，Ontology Manager 建对象，Functions 运行逻辑，Actions 写回，AIP/Agent 消费这些能力。

注意：以上是 Palantir 官方用于解释产品架构的业务示例，不应自动理解为对具体客户效果的独立验证。
03 · CLASSIC ARCHITECTURE

一般架构：Ontology 是怎么搭起来的？

最常见的系统不是“一张图”，而是从需求、模型、数据映射到查询和应用的一组层次。下面这套结构适用于 OWL/RDF 项目，也可以映射到企业对象平台。

6 · 应用与行动层搜索、分析、RAG/OAG、Agent、业务应用、受控 Actions。
5 · 语义服务层SPARQL 查询、图遍历、推理、SHACL 验证、API 与权限。
4 · 实例数据层具体对象与事实，例如 Flight A102、Aircraft N7 及它们的关系。
3 · 映射与集成层把数据库、CSV、API、文档抽取结果映射为统一对象和关系。
2 · Ontology 模型层Classes、Properties、Relations、Constraints、Rules；通常保存为 OWL/Turtle 等。
1 · 需求与治理层业务范围、验收问题、命名规则、负责人、版本、来源和变更流程。

最小 Setup 流程

1. 写问题列出系统必须回答的真实问题，即 competency questions。
→
2. 建模型定义 5–15 个核心类型和少量清晰关系。
→
3. 映射数据把现有表、API 或文档字段转换成对象和关系。
→
4. 存储查询装入 triple store，通过 SPARQL 或 API 查询。
→
5. 验证应用运行 SHACL/规则检查，再接搜索、RAG 或 Agent。
核心文件

你最终会得到什么？

ontology.ttl # 类型与关系 shapes.ttl # 数据约束 mapping.yaml # 原始数据如何映射 data.ttl # 实例数据 queries.rq # SPARQL 查询 README.md # 范围、负责人、版本
验收方法

怎么知道搭对了？

回到最初的问题实际查询。例如“哪些航班因同一架飞机的维护问题受影响？”如果模型不能稳定回答，说明类型、关系、映射或数据仍不完整。

先让 10 个高价值问题可回答，再扩展模型。

04 · OPEN-SOURCE STARTERS

开源平台：第一次上手选什么？

不需要先购买企业平台。下面这些工具分别解决“画模型、存数据、写代码、做验证、连接已有数据库”等问题。

首选入门低门槛

Protégé / WebProtégé

Stanford 维护的免费开源 OWL 编辑器。Desktop 适合本地学习，WebProtégé 适合多人协作。能建类、属性、实例并运行 reasoner。[8]

适合：第一次理解 OWL 和 Ontology 建模。
完整 Java 栈中等

Apache Jena + Fuseki

Jena 提供 RDF、OWL、推理和 SPARQL API；TDB 存储数据；Fuseki 将数据暴露为 HTTP SPARQL endpoint。[9]

适合：把 Ontology 做成可调用的服务。
Java 备选中等

Eclipse RDF4J

用于创建、解析、存储、推理和查询 RDF/Linked Data，可连接 SPARQL endpoint 与多种 RDF 数据库。[10]

适合：Java 应用和可替换的 RDF 存储后端。
Python 友好低—中

RDFLib + pySHACL

RDFLib 在 Python 中创建和查询 RDF；pySHACL 根据 SHACL shapes 验证数据质量。[11][12]

适合：BookRAG、数据抽取和快速原型。
连接现有 SQL中—高

Ontop

开源 Virtual Knowledge Graph 系统：通过映射把关系数据库虚拟呈现为知识图谱，不一定要把所有数据复制到图数据库。[13]

适合：数据主要已经存在 PostgreSQL、MySQL 等系统。
重要补充不是同一类

Neo4j 等图数据库

可以存节点和关系，但“用了图数据库”不代表自动拥有 Ontology。仍需定义类型、关系语义、约束、来源和治理。

适合：更偏 property graph 和遍历的项目。

直接给选择结论

只想学概念先用 Protégé 建一个航班或论文 Ontology，保存为 Turtle，运行一次 reasoner。
Python 项目用 RDFLib + pySHACL；模型仍可在 Protégé 中编辑。
需要服务用 Jena/Fuseki 或 RDF4J 提供存储、SPARQL 和 API。
已有大型 SQL评估 Ontop，通过虚拟映射减少数据复制。
05 · RAG VS OAG

RAG 与 OAG：运行逻辑有什么不同？

两者都在给 LLM 补充外部上下文。区别是：经典 RAG 主要围绕“找到相关内容”，广义 OAG 主要围绕“识别业务对象、连接关系、执行规则和受控行动”。

RAG · Retrieval-Augmented Generation

先找资料，再回答

像图书管理员：找到最相关的几页资料，交给 LLM 阅读。
1
建索引
文档切成 chunks，生成 embedding 或关键词索引。
2
检索
用户问题进入搜索，返回 top-k 相关片段。
3
重排
reranker 选择最相关且可用的证据。
4
生成
把问题和证据放入 prompt，LLM 生成带引用回答。

擅长：文档问答、政策检索、论文总结、客服知识库。

OAG · Ontology-Augmented Generation

先认清对象，再判断和行动

像运营值班经理：知道对象是谁、如何关联、处于什么状态以及能做什么。
1
建立世界模型
定义对象、关系、规则、Actions，并映射实时数据。
2
解析对象
把“A102”解析为唯一 Flight，把问题映射为对象路径。
3
查询与推理
遍历关系、读取状态、运行规则/Functions；必要时用 RAG 取原文。
4
生成并行动
LLM 解释方案；Action 在权限与审批下执行，结果写回形成反馈。

擅长：跨系统决策、多跳影响分析、实时运营和 Agent 工具治理。

同一个问题，两者会怎样处理？

问题：“A102 延误会影响谁？”RAGOAG
主要检索对象延误通知、操作手册、历史处置记录等文本。Flight A102、Aircraft、Crew、Passengers、Connections 等对象与状态。
关系处理关系通常藏在文本中，由检索或 LLM 临时理解。关系在模型中明确，可按 Flight → Aircraft → Issue 等路径遍历。
输出总结可能影响和处理建议，并引用材料。列出确切受影响对象、计算候选方案，并用 RAG 补充原文证据。
行动不属于经典 RAG 核心流程，需要额外接工具。Action 是 Operational Ontology 的一等能力，可做权限、条件、审批和审计。
建设成本较低，适合快速上线。较高，需要领域建模、映射、治理和持续维护。
最佳实践通常不是 RAG 或 OAG 二选一，而是 OAG 管对象与行动，RAG 找原文与证据。

例如 Ontology 先确定受影响的航班、飞机和乘客，再让 RAG 查维护记录与操作政策，最后由 Agent 形成方案并调用受控 Action。

术语边界：Palantir 官方已有 “Ontology-augmented generation” 页面；[5] 但 OAG 还不像 RAG 那样拥有高度统一的学术定义。相关方案也常被称为 ontology-grounded RAG、KG-RAG 或 ontology-aware agents。现代 RAG 也能连接 SQL、图谱和工具，因此两者是设计重心的区别，不是不可跨越的边界。
06 · SUMMARY

总结：Ontology 能做什么，接下来会走向哪里？

统一语义

让不同系统说同一种话

解决同名异义、异名同义、对象身份和跨系统字段不一致。

连接知识

从文本相似走向明确关系

支持对象查询、多跳遍历、来源追踪和跨系统影响分析。

约束质量

验证数据并辅助推理

利用类型、规则、SHACL 和 reasoner 发现冲突或推出隐含事实。

驱动行动

把建议变成受控操作

通过 Actions、权限、审批和审计，让人和 Agent 安全写回业务系统。

支持 Agent

提供稳定的世界模型

帮助 Agent 识别对象、选择工具、保存结构化记忆并评估执行过程。

促进复用

让模型跨应用共享

同一套对象、关系和规则可被搜索、分析、RAG、Agent 与业务应用共同使用。

值得关注的发展方向

1

Ontology + Agent

Ontology 成为 Agent 的世界模型、工具目录和行动边界，MCP/SDK 负责把能力暴露给模型。

2

RAG + OAG 混合检索

同时使用向量/BM25 的文本召回与对象/关系的结构化检索，提高多跳问题和可解释性。

3

实时数字孪生

把设备、订单、人员和事件的实时状态映射成可查询、可模拟、可行动的业务世界。

4

LLM 辅助建模

LLM 可从文档提出候选类型、关系和映射，但仍需 competency questions、验证规则和人工治理。

最终判断如果问题只是“从文档中找到答案”，先做 RAG；如果问题是“理解真实业务对象并让 Agent 安全行动”，再建设 Ontology/OAG。

从一个小领域、十几个真实问题和少量对象开始。Ontology 的价值不在模型画得多大，而在它是否真正支持查询、决策和行动。
